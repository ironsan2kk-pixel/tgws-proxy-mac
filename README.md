# TG WS Proxy for macOS

Локальный **SOCKS5-прокси для macOS**, который туннелирует трафик Telegram поверх **WebSocket** на официальные релеи `kws{dc}.web.telegram.org` — нативный аналог [tg-ws-proxy-android](https://github.com/LemoLev/tg-ws-proxy-ANDROID) (Flowseal-схема) в виде менюбар-приложения.

**Зачем:** там, где соединение с Telegram-серверами лежит в обходе (блокировки на стороне провайдера), этот прокси делает трафик неотличимым от обычного WebSocket к `*.web.telegram.org` — локально, без VPN и без root.

- ✅ **Без VPN, без root, без внешнего сервера** — ходит напрямую в официальные WS-релеи Telegram
- ✅ **Нативное macOS-приложение** (Swift/AppKit) — иконка в менюбаре, не в Dock
- ✅ **Меню-статистика**: сессии, WS-соединения, ошибки, байты
- ✅ **Автозапуск** и настройка порта
- ✅ **Лог ядра** всех сессий для диагностики
- ✅ **Приватный** по умолчанию (репо, а не проект — это про GitHub)

## Как это работает

```
Telegram Desktop / любой SOCKS5-клиент
        │  SOCKS5 127.0.0.1:1080 (без логина/пароля)
        ▼
TGWSProxyMac (менюбар)
        │  1. читает 64-байтный MTProto-obfuscation init
        │  2. определяет дата-центр (DC1..5, 203/204 → DC2)
        │  3. поднимает WebSocket к релею kws{dc}.web.telegram.org
        ▼
WebSocket binary-кадры → wss://kws{dc}.web.telegram.org/apiws
        │  (TLS + SNI = kws{dc}.web.telegram.org)
        ▼
Telegram DC2/DC4 :443
```

- **SOCKS5** (127.0.0.1, порт 1080 по умолчанию) — без логина и пароля.
- **Обфускация MTProto** — прокси определяет DC из первых 64 байт,
  «активированного» обфускационного init (AES-CTR, тег 0xEE/0xEF/0xDD).
- **Не-Telegram IP → passthrough** — остальной трафик идёт напрямую,
  прокси для него невидим.
- **TCP-fallback** — если WS-релей недоступен, идёт прямое соединение к DC.
- **HTTP-транспорт (браузеры) отклоняется** — прокси только для TG-клиентов.

## Установка

### Вариант 1 — готовое приложение (рекомендуется)

1. Скачайте `TGWSProxyMac.app.zip` из релизов — или возьмите
   `TGWSProxyMac.app` из папки `release/` в корне репозитория.
2. Распакуйте, скопируйте в **Программы** (или куда угодно).
3. Запустите двойным кликом — иконка появится в менюбаре (справа сверху).

> Первый запуск: macOS может предупредить об unsigned приложении.
> Правый клик по приложению → **Открыть** → подтвердите — одного раза достаточно.

### Вариант 2 — сборка из исходников

```bash
./build_app.sh        # собирает и подписывает TGWSProxyMac.app
```

Требуется macOS 14+, Xcode/Command Line Tools со Swift 5.10+.

## Использование

1. Запустите приложение → иконка в менюбаре.
2. Нажмите **«Включить»** (или вкл. автозапуск в настройках — стартует при входе).
3. Подключите Telegram:

**Telegram Desktop → Настройки (Ctrl+,) → Данные и память → Прокси →**
- Тип: **SOCKS5**
- Сервер: `127.0.0.1`
- Порт: `1080` (или порт из настроек приложения)
- Логин/пароль: **пусто**
- Сохранить → включить прокси.

4. Готово. В момент подключения в менюбар-меню виден счётчик сессий,
   в логе — по какому DC и через какой домен пошло соединение.

## Настройки

`~/Library/Application Support/TGWSProxyMac/config.json`:

```json
{"port": 1080, "autoStart": true}
```

- `port` — порт SOCKS5-сервера.
- `autoStart` — поднимать прокси при запуске приложения.

## Диагностика

**Лог ядра** — `~/Library/Application Support/TGWSProxyMac/core.log`
(пишется всегда, без ограничения в 50КБ, прокручивается в меню «Журнал»):

```
session: DC2 -> WS (домен kws2.web.telegram.org)
ws-connect(1): try dc2 ip=149.154.167.220 domain=kws2.web.telegram.org
ws-connect: OK dc2 via kws2.web.telegram.org
session: WS недоступен DC1 -> TCP fallback 149.154.175.50:443
session: passthrough -> 176.78.152.132:443
readSome: errno=54 (Connection reset by peer)
```

- `ws-connect(1|2)` — номер круга попыток; при пике релей может не принять
  первый connect, второй проходит.
- `WS недоступен … TCP fallback` — релей не поднялся, работаем напрямую.
- `readSome: errno=54` — клиент оборвал соединение (норма, не ошибка).

**Отладка WS** — запустить с переменной `TGWS_DEBUG=1` (хвосты кадров).

## Частые проблемы

| Симптом | Причина/решение |
|---|---|
| Порт 1080 не слушает | Нажмите «Включить»; проверьте лог; нет ли другого процесса на 1080: `lsof -nP -i :1080` |
| «Не удалось найти прокси» в TG | Добавьте прокси как SOCKS5, сервер `127.0.0.1`, порт из настроек |
| Медиа/фото не качаются | Медиа-поток идёт на media-домен (`kws2-1`); проверьте лог — должно быть `DC2 media -> WS` |
| Всё работает мгновенно, потом соединения рвутся | Смотрите «WS недоступен … fallback»: релей может не отвечать на пике — реализованы 2 попытки; см. таблицу релеев ниже |
| TG-клиент на iOS/Android | Через SOCKS5 с 127.0.0.1 не работает (надо MTProto-прокси); для мобильных есть tg-ws-proxy-android |
| Упоминается SIGPIPE | Глянуть unified log: `log show --last 1h --predicate 'eventMessage CONTAINS "SIGPIPE"'` — приложение не должно умирать; если падает — отправьте лог |

## Релеи и DC (проверено 09.09.2026)

С **этого клиента** WS-релеи Telegram отвечают только на IP `149.154.167.220`
(это релей-интерфейс DC2/DC4); DNS-имена `kws{dc}.web.telegram.org` резолвятся
в другие IP (`149.154.167.99`, `149.154.174.100`, `149.154.170.100`), которые
с этой сети недоступны вообще.

| Домен | IP к релею | Результат |
|---|---|---|
| kws2.web.telegram.org | 149.154.167.220 | ✅ 101 (основной DC2) |
| kws2-1.web.telegram.org | 149.154.167.220 | ✅ 101 (media DC2) |
| kws4.web.telegram.org | 149.154.167.220 | ✅ 101 (основной DC4) |
| kws4-1.web.telegram.org | 149.154.167.220 | ✅ 101 (media DC4) |
| kws1/3/5.web.telegram.org | любые | ⚠️ connect timeout → TCP fallback |

DC1/DC3/DC5 при недоступности релеев уходят в TCP-fallback. Это не мешает
работе Telegram — аккаунт живёт на DC2/DC4, они обслуживаются через WS.

Внутри `tryConnectWS`: **2 полных круга** по доменам (первый connect при
пике может не пройти), таймаут 6 сек, **кэш успешного домена** на DC.

## Как собрано (краткая архитектура)

```
App/
├── Package.swift            # SwiftPM: Core + Mac (UI) + Test (харнесс)
└── Sources/
    ├── TGWSProxyCore/       # ядро без AppKit
    │   ├── CTR.swift        # AES-128-CTR (CommonCrypto, без зависимостей)
    │   ├── MTProto.swift    # DC-таблицы, парсинг/patch init, MsgSplitter
    │   ├── WSClient.swift   # raw WebSocket (NWConnection + TLS SNI)
    │   └── SOCKS5.swift     # SOCKS5-сервер + WS/passthrough/fallback-мосты (poll)
    ├── TGWSProxyMac/        # менюбар-приложение (AppKit)
    └── TGWSProxyTest/       # тест-харнесс (bin: TGWSProxyTest <port>)
```

Подробности — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Проверено

- ✅ **GramJS** (реальный MTProto-клиент) через прокси: `CONNECTED TO DC`
  — полный auth-хендшейк (req_pq → resPQ → DH);
- ✅ **стресс**: 8 параллельных сессий — 8/8;
- ✅ **passthrough**: `curl -x socks5h://127.0.0.1:1080 https://google.com` → 301 за 0.1с;
- ✅ **SIGPIPE**: 20 жёстких разрывов на середине трафика — процесс жив;
- ✅ **WS-хардшейк** к kws2/kws2-1/kws4/kws4-1 → 101.
- ✅ **автозапуск**: рестарт + `open` поднимает порт, дублей нет.

## Известные ограничения

- **IPv6** не поддерживается (как в референсе) — отклоняется.
- **Пул/кулдаун релеев** не перенесены — каждое TCP-соединение = свой WS-поток.
- **fake-TLS-прокси** (`ee`-секрет) не реализован — только SOCKS5.
- **iOS/Android** клиенты через этот прокси не работают (нет локального SOCKS5
  на устройстве) — используйте tg-ws-proxy-android либо настройте на стороннем
  смартфоне/планшете через прокси на этом Mac.
- Порог 4-6с на WS (таймаут connect), далее fallback — при пиковой нагрузке
  релея может заметно медленнее, чем при прямом соединении.
